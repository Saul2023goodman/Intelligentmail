# Execution Queue Design · 执行队列重构方案

Status: proposed · Owner: Operator-facing Execution route (`frontend/src/pages/execution/`)

本文档替换当前 Execution 页的六面板布局。它先陈述**需求本质**（为什么现状是错的），再给出
状态模型、信息架构、时间线网格规格、交互流程，最后是后端与前端的实施增量和验收标准。

---

## 1. 需求本质

### 1.1 现状错在哪里

`propose_plan` 把 Campaign 内**全部** Ready 的 Preparation 按固定间隔串成**一条全局队列**：

```
Harvard A 09:00 → Harvard B 09:15 → Harvard C 09:30 → Yale A 09:45 → …
```

这条队列有两个后果：

1. **它排的是"邮件数"，不是"风险"。** 间隔 15 分钟是任意的，跟任何真实约束都无关。
2. **它制造了真正的风险。** 同一所院校的几位导师在半小时内先后收到同一个申请人的邮件，
   他们会互相交流，套磁的可信度当场失效。这是申请人最不能接受的结果。

### 1.2 真正的约束

> **同一档期内，同一院校最多出现一位导师。不同院校在同一档期内并行。**

院校之间没有信息交换，所以并行是安全的；院校内部有，所以必须串行。这就是"区分化的定时"
——区分的单位不是"第几封邮件"，而是"哪所学校的第几位导师"。

### 1.3 档期（Session）的定义

**档期 = 一个允许窗口在某一天的一次出现。** 它直接由现有 `windows` 配置推出，不引入新概念：

| 配置 | 档期 |
| --- | --- |
| `MON-FRI 09:00-17:00` | 每个工作日一个档期 |
| `MON-FRI 09:00-12:00` + `MON-FRI 14:00-17:00` | 每个工作日两个档期（上午档 / 下午档） |

档期是**轮转的节拍**。第 r 个档期让每所还有第 r 位待发导师的院校各出一位：

- **校内串行**：Harvard 的第 1、2、3 位导师落在第 1、2、3 个档期。
- **校间并行**：Harvard 第 1 位与 Yale 第 1 位同在第 1 个档期，按 `spacing_minutes` 错开分钟。
- `daily_limit` 继续约束每个本地日的总量；`spacing_minutes` 继续约束同一档期内的分钟错开。

**收益**：一轮套磁所需天数 = `max(单校导师数)`，而不是 `总数 ÷ daily_limit`。
45 人分 12 所院校、最多一校 6 人 → 约 6 个档期（一周）完成，而不是 45 封排队。

### 1.4 两个由此确立的规则

- **只有 Ready 能进入执行队列。** Readiness 是唯一入口闸门；未就绪的动作带着阻塞原因留在
  池外，永不出现在时间线上。Readiness 仍然不是授权（Authorization）。
- **定时好并确认 = 已进入可发送队列。** 一个格子拿到精确时间并取得 Confirmation，它就是队列
  成员。不存在第三个需要单独维护的状态。

## 2. 状态模型

```
未就绪 ──▶ 已排期 ──▶ 已入队 ──▶ 发送中 ──▶ 已发送
 (blocked)  (proposed)  (queued)   (sending)   (sent)
                          │
                          └──▶ 失败 / 未知 / 已过档期
```

| 状态 | 来源 | 含义 |
| --- | --- | --- |
| `blocked` | readiness blocking finding | 不进队列。界面上只给出原因 |
| `proposed` | 排期已生成，未确认 | 有时间，还不是队列成员 |
| `queued` | Confirmation 已建立 | **已进入可发送队列** |
| `sending` | run 正在执行 | 观测中的瞬时状态 |
| `sent` / `failed` / `unknown` | 邮箱证据 | 观测结果，永不推断 |
| `expired` | 时间已过且未执行 | 需要显式改期，绝不降级为立即发送 |

`proposed` 与 `queued` 在时间线上是**同一个格子的两种颜色**，不再各占一个面板。

## 3. 信息架构：六区 → 三区

### 删除

| 现有面板 | 去处 |
| --- | --- |
| **Proposed slots** | 它就是时间线网格本身。作为卡片列表它只是"同一批卡片加了时间"，无信息增量 |
| **Timeline** | 时间线网格从左到右就是时间顺序。独立事件流水账重复了同一批数据 |
| **Awaiting execution** | 并入格子状态（`queued`）与执行观测 |
| **Authorize and run** | 降级为时间线工具栏上的两个动作 |

四个面板都是同一份数据的不同投影。删除它们不是减少功能，是消除重复。

### 保留并重组

```
┌──────────────┬────────────────────────────────────┬──────────────┐
│  就绪池       │        发送时间线（主视觉）          │  执行观测     │
│  Ready pool  │    档期 × 院校 网格 + 现在线         │  Execution   │
│              │                                    │  monitor     │
│  按院校分组   │  行 = 院校  列 = 档期  格 = 一位导师  │  队列 + 进度  │
│  只有 ready  │  格内状态色 = 排期/入队/发送中/结果    │  + 结果      │
│  未就绪折叠   │                                    │              │
└──────────────┴────────────────────────────────────┴──────────────┘
```

桌面三栏；窄窗口仍用现有 tab 切换，但只有三个 tab。

## 4. 时间线网格规格

### 4.1 结构

- **行 = 院校**（`institution_name`）。行头 sticky 左置，显示院校名 + 该校在本计划中的导师数。
- **列 = 档期**。列头显示日期（今天 / 明天 / 9月21日 周一）+ 窗口时段 + 该档期已排数。
- **格 = 0 或 1 位导师**：导师名 + `HH:MM` + 状态标记。
- **空格 = 该校本档期不投**。用极淡虚线占位表示——它是**刻意的留白**，不是缺失数据。
- **现在线**：一条贯穿网格的细竖线。左侧档期为过去，右侧为未来。到期未发的格子在左侧显形。

### 4.2 格子状态语言

沿用现有 `ex-chip` 色板，新增两个状态：

| 状态 | 左侧竖条 | 底色 | 语义 |
| --- | --- | --- | --- |
| `proposed` | `#5a91ff` 蓝 | `#f2f7ff` | 已排期，未入队 |
| `queued` | `#3379ff` 靛蓝 + 实心点 | `#e4efff` | **已进入可发送队列** |
| `sending` | `#3379ff` + 脉冲 | `#e4efff` | 执行中 |
| `sent` | `#28bd8d` 绿 | `#e2f6ea` | 邮箱确认已发送 |
| `failed` | `#e05a4a` 红 | `#fdeae8` | 邮箱报告失败 |
| `unknown` | `#ffba35` 琥珀 | `#fdf1dc` | 证据不足，需对账 |
| `expired` | `#bccadf` 灰 | `#eef2f8` | 时间已过，需显式改期 |

### 4.3 约束的视觉表达

**"同校每档期一位"必须是看得见的规则，不只是算法。** 因此：

- 每一行每一列**最多一格**，网格天然呈现这条约束。
- 悬停某行时高亮该校在所有档期上的序列，让"校内串行"一眼可读。
- 悬停某列时高亮该档期所有院校，让"校间并行"一眼可读。
- 试图把某位导师改到本校已占用的档期时，直接在格子上给出拒绝原因。

## 5. 交互流程

1. **排期** — 就绪池工具条「生成排期」：`execution_propose`。按院校轮转规则给所有 ready
   分配时间，网格出现，全部为 `proposed`。
2. **入队** — 网格工具条「确认入队 N」：一次评审全部邮件（`execution_review` →
   `execution_confirm`），全部转为 `queued`。**此步之后它们就是队列成员。**
3. **执行** — 执行观测区「发送到期项」：对时间已到的 `queued` 项发起
   `execution_run`。运行中格子依次变 `sending` → 结果色，观测区同步滚动。
4. **单格** — 点击格子打开检查器：完整邮件正文、精确时间、改期、移出本档期、单独执行。
   改期受"同校同档期唯一"约束，违规被明确拒绝。

### 5.1 执行观测区

- **队列清单**：按时间排序，每项显示 时间 / 院校 / 导师 / 状态 / 距到期倒计时。
- **当前运行**：进度条 + 当前项 + 已观测结果（沿用 `ExecutionRun` 的
  `requested / reached / not_reached` 语义）。
- **能力横幅**：某类执行不可用（如原生定时未启用）时，只禁用它自己的区域并说明依据，
  不隐藏其他路径。

## 7. 验收

- [ ] 未就绪的 Preparation 不出现在时间线上；就绪池外能看到其阻塞原因
- [ ] 同一档期内同一院校最多一格；同一院校的导师按档期顺序串行
- [ ] 确认后格子变为"已入队"，且执行观测区立刻列出它们
- [ ] 执行过程中格子状态在页面上就地变化，无需跳转
- [ ] 时间已过未执行的格子标记为"需改期"，不提供立即发送
- [ ] 窄窗口三个 tab 均可达，无页面级滚动
- [ ] `tests/test_plan.py` 全绿；新增用例覆盖多院校轮转与 `institution_pace`
