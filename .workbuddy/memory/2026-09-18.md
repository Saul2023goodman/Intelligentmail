- `src/shared/primitives.css` has a **global** `h1` + `h1 span` pill style. Any span
  inside a shared `h1` inherits the pill; `.page-title` / `.page-subtitle` must
  explicitly reset `background/border/padding`.
- `button { display: inline-flex }` from `index.css` means `.mb-stat` cards are flex
  rows, not stacks — their span/strong/small sit side by side.
- Never ellipsize the page title. `.page-header` uses `flex-wrap: wrap` plus
  `.page-header-copy { min-width: min-content }` so meta/actions wrap below instead of
  truncating the title at 390px.

Created `.scratch/smartmail-phase-one/issues/13-batch-execution-runs.md`. Operator
direction confirmed by the user: (1) authorization + execution merge into one primary path

## Ticket 13 implemented: Execution Runs

- New `smartmail/_operations/runs.py` (`RunOperations`, mixed into `SmartMail`): `run_batch`,
  `get_execution_run`, `list_execution_runs`, `execution_queue`, plus restart reconciliation
  (`_reconcile_running_runs`, hooked into `_recover_unfinished_execution`) and
  `_note_resolved_attempt`, which keeps a run item honest after Reconciliation.
- `schema.sql`: `execution_runs`, `execution_run_items` (`UNIQUE(run_id, sequence)`).
- `execution_run` (UI) accepts `confirmation_id` *and* `confirmation_ids`; a one-item run
  still returns the legacy shape (`attempts`/`paused`/`flow`/`schedule`/`replacement_placed`)
  via `_run_result`, so old callers and tests keep working. `execution_confirm` adds a
  `confirmations` key for plan/cancellation/replacement (immediate already returned a list).
- New UI commands `execution_runs`, `execution_run_show`, `execution_queue`; new CLI
  `execution batch|runs|run-show|queue` (`execution run` unchanged: immediate single path).
- Frontend: `ExecutionPage` reads `queue`/`runs`/`availability` from `execution_workspace`;
  selection defaults to every `ready_to_authorize` row (derived in render, not an effect —
  oxlint flags set-state-in-effect); "Review and send N" + "Authorize only", separate
  immediate/scheduled regions each stating scope, result dialog with per-outcome summary.
- Decision: `native_scheduling` default **not** reversed (ticket 12 still `live-acceptance-partial`);
  availability is now per-kind so scheduling is no longer behind the immediate-send capability.
- Deviation from the ticket's outcome enum: non-immediate runs record `externally_scheduled`,
  `cancelled`, `replaced` instead of `sent` — the glossary forbids calling an externally
  scheduled draft Sent, and removal is not a send.

## Execution 页重构设计方案（UI designer 会话, 晚）

- 需求本质: 现状 `propose_plan` 把全部 Ready 排成**一条全局等间隔队列**（45 封 × 15 分钟），
  排的是"邮件数"不是"风险"；同一院校的导师可能只隔 15 分钟收到同一申请人的信 → 群发暴露。
  真约束是 **同校每个档期只发一位导师，不同院校同档期并行**。
- **档期 = 一个允许窗口在某一天的一次出现**，直接由现有 `windows` 配置推出，不新增概念。
  轮转规则：第 r 档期让每所还有第 r 位待发导师的院校各出一位 → 校内串行、校间并行；
  完成天数 = `max(单校导师数)` 而非 `总数 ÷ daily_limit`。
- 产出 `docs/execution-queue-design.md`（状态机 / 六区→三区 IA / 网格规格 / 后端增量 / 验收）
  与 `output/execution-queue-prototype.html`（可点击原型：生成排期 → 确认入队 → 发送到期项，
  格子就地变状态）。**尚未改动生产代码。**
- 关键兼容性发现: `tests/test_plan.py` 的所有 Supervisor 同属 `Example University`（单院校），
