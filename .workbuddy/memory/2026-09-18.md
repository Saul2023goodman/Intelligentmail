## Frontend: unified page header + density compression

- Added `frontend/src/app/page-header.tsx` + `page-header.css` — the single shared page
  title band. Props: `eyebrow`, `title`, `badge`, `subtitle`, `meta`, `actions`.
  Shell owns the rhythm; pages pass their own actions/meta only.
- `src/app/viewport.css` now owns the whole chrome budget via `.app-shell` variables:
  `--bar-height` (topbar), `--heading-block` (header band), `--toolbar-height`
  (first-level/column headings), `--region-inset`, `--page-inset`, `--page-title`.
  Chrome must size from these; no fixed pixel paddings in page CSS.
- Removed Mailbox's oversized `mb-heading` block (eyebrow + 28px h1 + deck paragraph +
  separate `mb-controls` row) and replaced it with the shared header; stats/toolbars/
  rows compressed. Net chrome at 1440×900 went ~325px → ~179px.
- Records / Review / Execution switched to `PageHeader`; Intake and Workflow keep no
  title band but consume the same density variables (column headings use
  `--toolbar-height`, board/student bar use `--page-inset`).

### Gotchas learned
- `src/shared/primitives.css` has a **global** `h1` + `h1 span` pill style. Any span
  inside a shared `h1` inherits the pill; `.page-title` / `.page-subtitle` must
  explicitly reset `background/border/padding`.
- `button { display: inline-flex }` from `index.css` means `.mb-stat` cards are flex
  rows, not stacks — their span/strong/small sit side by side.
- Never ellipsize the page title. `.page-header` uses `flex-wrap: wrap` plus
  `.page-header-copy { min-width: min-content }` so meta/actions wrap below instead of
  truncating the title at 390px.

### Browser verification recipe (reusable)
Playwright browsers exist at `%LOCALAPPDATA%\ms-playwright\chromium_headless_shell-1234`
while the cached `@playwright/cli` expects `-1244`, so `npx playwright-cli` fails.
Instead drive it directly with `executablePath`:

```js
const require = createRequire("C:/Users/Zeng/AppData/Local/npm-cache/_npx/31e32ef8478fbf80/node_modules/");
const { chromium } = require("playwright");
chromium.launch({ executablePath: "C:/Users/Zeng/AppData/Local/ms-playwright/chromium_headless_shell-1234/chrome-headless-shell-win64/chrome-headless-shell.exe" })
```

Dev server: `cd frontend && npm run dev -- --port 5179 --strictPort` (system `python`
already has openpyxl/tzdata, so the Core stdio bridge works without `.venv`).

## Follow-up activation analysis (chat only)

Read-only analysis of `_operations/followups.py`. Key findings: activation is pure
lazy evaluation (`_task_follow_up_view`), no timer/daemon; `prepare_follow_ups` (CLI only)
is the only writer; anchor = latest Sent Record's `outcome_observed_at ?? intent_at` +
`delay_days` so follow-ups chain; automatic replies never block, ambiguous ones park the
Task in `reply_review_required`. Gaps found: no `DELETE FROM follow_up_actions` and no
abandoned/cancelled status, so an action created but never sent pins the Task in
`follow_up_open` forever; rules are read live (no snapshot, unlike Sending Plans); the
frontend has no activation entry point at all (read-only via `records_ui.py`).

## Batch execution refactor → ticket 13

Created `.scratch/smartmail-phase-one/issues/13-batch-execution-runs.md`. Operator
direction confirmed by the user: (1) authorization + execution merge into one primary path
with "authorize only" kept secondary; (2) one batch = one Core call that stops on a pause

`execution_run_items`, outcome includes `not_reached`), not derived in the UI; (4)
scheduling is core functionality with `native_scheduling` supported by default — which
conflicts with current gating (`--enable-extension-schedule`, `verified: false`, ticket 12
`live-acceptance-partial`), so that decision is recorded as a blocker in the ticket's
Comments rather than assumed.
