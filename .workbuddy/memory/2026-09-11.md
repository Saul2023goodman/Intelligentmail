## Ticket 07: Detect historical duplicates before execution (resolved)

Implemented ticket 07 at the same core/CLI seam, TDD red→green per vertical slice. Final ordinary run: **136 tests passed, 5 skipped** (120 prior + **16 new** in `tests/test_duplicates.py`; the 5 skips are the `SMARTMAIL_SAMPLE_ZIP` opt-in representative tests).

**Confirmed the seam with the user before writing tests (4 decisions):**
1. Dedicated `duplicate` command group (`check|list|show`) with a **persisted** `duplicate_checks` record per check (finding, matches, Evidence Coverage) rather than folding findings into the mailbox reconciliation output.
2. **Minimal action-kind + link marker now, not deferred to ticket 16**: `preparations.action_kind` (default `initial`) + optional link to earlier outreach, frozen into the Sent Record; `preparation link-follow-up` marks a linked Follow-up Action so it is never reported as duplicate initial outreach.
3. Matching model is **mailbox account → Student, recipient → Supervisor**. Only *incomplete* or *conflicting* evidence requires review — no extra ambiguity categories.
4. **Incomplete coverage never blocks on its own**; No Duplicate Found stays qualified by coverage.

**Implementation**: new `duplicate_checks` table; `preparations` gained `action_kind` + `linked_sent_record_id`, `sent_records` gained `action_kind` + `follows_sent_record_id` (added both in `schema.sql` and via an idempotent `_migrate` loop over `(table, column, ddl)` tuples — follow the same pattern for future columns). `_record_sent` had to switch from positional `INSERT INTO sent_records VALUES (...)` to explicit columns because of the new columns. Findings: `repeat_execution`, `duplicate_suspicion`, `ambiguous_match` (bases `conflicting_identity` / `incomplete_evidence`), `linked_follow_up`, `no_duplicate_found`; `_REVIEW_FINDINGS` drives `review_required`. `run_execution` now re-checks after authorization and before creating an Attempt and pauses the flow on a review-required finding.

**Deliberate non-changes** (to keep 120 prior tests green): Repeat Execution, changed content and new readiness blockers are still *refused* by `_authorized_request`; only newly discovered duplicate/ambiguous evidence *pauses*. Identity conflict at the readiness level still raises; the duplicate-level `conflicting_identity` is resolved by the existing `task confirm-identity`.

**Notable constraint discovered**: a Task can only ever have **one active Preparation** (`prepare` records `replacement_requires_rewrite`; `rewrite` refuses after Sent), so "a prior initial-outreach Sent Record on the same Task from a *different* Preparation" is unreachable through the public seam. Duplicate suspicion therefore comes from mailbox observations (history predating SmartMail); that branch was deliberately not written as untested code.

**Pilot** (`.smartmail/ticket07-pilot.py`, gitignored): no history → `no_duplicate_found` (coverage incomplete, 2 limitations); after observing one prior outbound send → `duplicate_suspicion`, basis `known_supervisor_address`, coverage complete; `execution run` on the pre-existing Confirmation → `paused`, reason `duplicate_suspicion`, 0 attempts, Confirmation still active. Store retained three checks: `no_duplicate_found`, `duplicate_suspicion`, `duplicate_suspicion`.

**Docs**: `docs/duplicate-pattern-07.md`, `docs/ticket-07-validation.md`; README updated ("Tickets 01 to 07", new "Detect historical duplicates before execution" section); ticket 07 marked resolved with a comment. Next: ticket 08 (recover execution and takeover).
